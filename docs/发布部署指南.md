# 部署脚本使用说明

所有相对路径均以源码根目录为例。脚本根据自身位置查找文件，不要求终端当前目录与脚本目录一致。
Windows PowerShell 脚本使用 UTF-8 BOM，以兼容 Windows PowerShell 5.1；Linux shell 脚本使用 LF 换行。

## 脚本入口

| 场景 | 中文脚本 |
| --- | --- |
| Windows 安装/配置服务 | `script/windows/安装Windows服务.ps1` |
| Windows 卸载服务 | `script/windows/卸载Windows服务.ps1` |
| Linux 安装/更新服务 | `script/linux/发布Linux服务.sh` |
| Linux 卸载服务 | `script/linux/卸载Linux服务.sh` |
| Windows 终端部署 Docker | `script/docker/发布Docker.ps1` |
| Windows 终端卸载 Docker | `script/docker/卸载Docker.ps1` |
| Linux 终端部署 Docker | `script/docker/发布Docker.sh` |
| Linux 终端卸载 Docker | `script/docker/卸载Docker.sh` |
| 生成安装/升级 ZIP | `script/windows/生成安装升级包.ps1` |

脚本以中文名为唯一入口，已移除英文兼容脚本。卸载脚本只移除服务或容器，不删除程序、现场配置、数据文件、数据库或 Docker 数据卷。

## 打包与移动路径

打包电脑需要 .NET 10 SDK、Node.js/npm，以及前端依赖。若尚未安装前端依赖，先在 `src/IPC.Gateway.Web` 中安装依赖。
运行目标电脑需要 ASP.NET Core Runtime 10；运行发布后的前端不需要 Node.js。

在 VS Code 中打开整个源码文件夹，然后打开 PowerShell 终端。第一次取到代码时，先进入 `src/IPC.Gateway.Web` 安装前端依赖，再回到源码根目录；后续中文打包脚本会自动编译前端并发布后端与协议驱动。

```powershell
Push-Location .\src\IPC.Gateway.Web
npm ci
Pop-Location
```

Windows 发布选择 `win-x64`；在 Windows 开发电脑上为 Linux 打包也可以，按目标选择 `linux-x64` 或 `linux-arm64`。
首次部署用 `-PackageType Install`，后续更新用 `-PackageType Upgrade`。默认输出在源码根目录的 `artifacts/packages`，可以在资源管理器直接找到 ZIP。
解压后应检查 `payload/IPC.Gateway.WebHost.dll`、`payload/wwwroot/index.html` 和 `payload/Drivers` 均存在。

```powershell
& .\script\windows\生成安装升级包.ps1 -PackageType Install -RuntimeIdentifier win-x64
& .\script\windows\生成安装升级包.ps1 -PackageType Upgrade -RuntimeIdentifier linux-x64
```

ARM64 Linux 使用 `-RuntimeIdentifier linux-arm64`。目标协议的本机依赖也需要支持该平台，尤其串口、ADS 和 DNP3 等驱动应在目标系统验证。
当前脚本生成需要已安装 .NET 运行时的发布包，不把 .NET Runtime 本身包含在 ZIP 中。

- **整个源码目录换盘或改名**：可以继续打包，保留源码内部目录结构即可。
- **只把打包脚本单独移动**：脚本已包含完整实现，复制后指定 `-RepositoryRoot` 指向包含 `src` 的源码根目录。
- **输出位置改变**：使用 `-OutputDirectory`，可以是绝对路径或相对于调用时当前目录的路径。
- **跨平台**：选择对应 RuntimeIdentifier，不要将 Windows 平台专用包当作 Linux 包安装。

例如，脚本复制到其他位置后：

```powershell
& 'D:\发布工具\生成安装升级包.ps1' -RepositoryRoot 'D:\源码\ipc.gateway' -OutputDirectory 'D:\发布包' -RuntimeIdentifier linux-x64 -PackageType Upgrade
```

不指定平台时保留原有通用发布行为；正式部署建议明确指定目标平台。包名和包编号会带目标平台后缀，防止不同平台的同版本包互相覆盖。
ZIP 根目录包含清单、`payload` 和 `tools`。中文安装/卸载脚本也会随包附带；Docker 工具位于 `tools/docker`。
使用 `-NoRestore` 时，需要先为相同 RuntimeIdentifier 还原依赖；离线环境还需要提前准备对应运行时依赖。

## Windows 服务安装与卸载

1. 将 Windows 发布 ZIP 解压到一个临时目录。
2. 将 `payload` 内的程序文件复制到正式程序目录，例如 `E:\IPCGateway\app`。它应包含 DLL、`wwwroot`、`Drivers` 等。
3. 配置正式程序目录的 `appsettings.Production.json`，设置 SQL Server 连接、认证密钥等。更新时保留原配置和密钥。
4. 以管理员身份打开 PowerShell，执行安装脚本。第一次安装建议先不加 `-Start`，检查配置后再启动。

```powershell
& .\script\windows\安装Windows服务.ps1 -PublishDirectory E:\IPCGateway\app -DataDirectory E:\IPCGateway\data -EnableServiceRecovery
```

安装成功后，通过 Windows“服务”窗口启动 IPCGateway；也可以在安装时加 `-Start`。
脚本支持重复执行来更新服务路径；已有服务环境变量中的数据库连接和密钥会保留，显式传入的参数/环境变量覆盖同名项。
程序替换前必须先停服务，勿直接覆盖正在运行的程序文件。Windows 界面 ZIP 自动升级流程见 [ZIP 升级操作指南](ZIP升级操作指南.md)。

```powershell
& .\script\windows\卸载Windows服务.ps1
```

卸载会等待服务进程退出并移除服务注册；程序和数据仍保留。

SQL Server 需要提前安装，连接字符串指定的数据库需要已存在且账号具备建表/读写权限；脚本不安装数据库，也不会自动把开发电脑的数据库复制到目标电脑。要保留已有设备、标签、账号等配置，应使用现有数据库，或先通过 SQL Server 备份/还原迁移数据库。

## Linux systemd 发布与卸载

适用于使用 systemd 的 Linux；需要 `bash`、`rsync`（支持 `--chown`）、`realpath`、用户管理工具，以及 ASP.NET Core Runtime 10。
在打包电脑生成 `linux-x64` 或 `linux-arm64` 的 ZIP，再传输到 Linux 解压。
安装目录、数据目录、环境文件和 dotnet 路径使用不含空格的绝对路径。解压目录可以包含空格。

```bash
sudo bash script/linux/发布Linux服务.sh /tmp/ipc-release/payload
```

默认安装到 `/opt/ipc-gateway/app`，数据放在其 `Data` 子目录，环境文件为 `/etc/ipc-gateway/ipc-gateway.env`，服务名为 `ipc-gateway`。
首次安装默认不启动。参考 `script/linux/gateway.env.example` 编辑该环境文件，配置 SQL Server、认证密钥、数据加密主密钥及首次管理员密码，再启动服务。
也可以使用现场的 `appsettings.Production.json`；首次安装会复制发布目录中已有的生产配置，后续不覆盖。

```bash
sudo systemctl start ipc-gateway
sudo systemctl status ipc-gateway
sudo journalctl -u ipc-gateway -f
```

自定义路径、监听地址：

```bash
sudo INSTALL_DIR=/opt/ipc-gateway/app DATA_DIR=/var/lib/ipc-gateway SERVICE_URL=http://0.0.0.0:5184 START_SERVICE=1 bash script/linux/发布Linux服务.sh /tmp/ipc-release/payload
```

首次自定义路径后，后续更新必须使用相同的 `INSTALL_DIR`、`DATA_DIR`、`ENVIRONMENT_FILE` 和 `SERVICE_NAME`。
脚本复制前会停止正在运行的同名服务，保留 `Data`、`logs`、`appsettings.Production.json` 和外部数据目录，复制后恢复原本运行的服务。
如果原来服务已停止，则仅在 `START_SERVICE=1` 时启动。程序目录不应放置需要保留的其他自定义文件；更新会清理过期程序文件。

```bash
sudo bash script/linux/卸载Linux服务.sh
```

自定义服务名时，卸载也要传入相同 `SERVICE_NAME`。卸载不删除服务用户、程序目录、环境文件或数据。

## Linux 是否支持 ZIP 升级

**支持以 ZIP 交付，解压后通过发布脚本更新；目前不支持网页一键自动执行。**
当前程序的自动执行器仅支持 Windows 服务，生成的离线执行脚本也是 PowerShell/Windows 服务流程。
Linux 网页可以上传并校验 ZIP，但不要把“上传成功”理解为 Linux 自动升级已经实现，也不需要点击“准备升级”来进行以下人工更新。

人工更新步骤：

1. 在目标 Linux 平台验证驱动兼容性，备份 SQL Server 数据库、现场配置和程序文件。
2. 使用对应 Linux RuntimeIdentifier 生成 Upgrade ZIP，并核对发布者提供的 SHA256。
3. 上传到 Linux，解压到一个新的临时目录，不能直接解压覆盖正在运行的安装目录。
4. 在维护窗口执行上面的 `发布Linux服务.sh`，源目录选择新 ZIP 的 `payload`。也可使用 ZIP 附带的 `tools/发布Linux服务.sh`。
5. 脚本停止服务、保留配置和数据、同步程序后恢复原运行状态。检查日志、`/health/ready`、设备和标签读数。
6. 若程序更新失败，使用备份的旧程序目录作为发布源恢复。人工脚本流程不会自动生成网页回滚点；数据库恢复需单独处理。

不要在两个 Linux 目录之间改用不同的本机派生加密密钥；迁移加密配置时应保持显式主密钥一致。

## Docker 发布与卸载

需要 Docker 引擎和 Docker Compose v2。默认使用 `docker-compose.external-db.yml`，连接现有 SQL Server，不新建数据库容器。
保留原 `docker-compose.yml` 作为带 PostgreSQL 的示例，需要时可通过参数明确选择。

首次将 `script/docker/gateway.env.example` 复制为同目录的 `gateway.env`，填写数据库地址、认证/加密密钥和管理员初始密码。
Linux 上建议将环境文件权限设为仅管理员可读，或使用生产环境现有的凭据管理方式。
容器中的 `127.0.0.1` 是容器本身；连接宿主机 SQL Server 应使用宿主机局域网地址或 `host.docker.internal`，并确保 SQL Server TCP 端口可访问。

Windows PowerShell：

```powershell
& .\script\docker\发布Docker.ps1
& .\script\docker\卸载Docker.ps1
```

Linux Bash：

```bash
bash script/docker/发布Docker.sh
bash script/docker/卸载Docker.sh
```

默认从当前源码构建镜像并后台启动。重复发布会重新构建并更新容器，保留数据卷。
如果是在无源码的交付环境，先加载发布镜像，使用相同镜像名指定 `-NoBuild` 或 `NO_BUILD=1`：

```powershell
& .\script\docker\发布Docker.ps1 -NoBuild -Image ipc-gateway:2026.11.07
```

```bash
NO_BUILD=1 IMAGE=ipc-gateway:2026.11.07 bash script/docker/发布Docker.sh
```

PowerShell 可使用 `-RepositoryRoot`、`-ComposeFile`、`-EnvironmentFile`、`-ProjectName`，Bash 对应 `REPOSITORY_ROOT`、`COMPOSE_FILE`、`ENVIRONMENT_FILE`、`PROJECT_NAME`。
卸载需要与安装使用相同的 Compose 文件、环境文件和项目名；不要在更新时更换项目名，否则会指向新的数据卷。
卸载脚本执行普通 `compose down`，不带 `--volumes`，不删除镜像或外部 SQL Server 数据库。
容器更新应通过新镜像和重新创建容器完成；不使用网页 ZIP 替换容器内部程序。
容器内 `/app/Data` 的历史、队列、证书、模型和脚本配置已映射到持久化数据卷。

默认网站端口为 5184。容器启动后需要检查 `docker compose logs`、`/health/live`、`/health/ready` 和实际设备通信；脚本成功不等于所有外部设备均已连接。

源码在有 Docker 的开发电脑上时，`发布Docker` 脚本可直接构建镜像并启动，镜像就是 Docker 的交付包。如果生产电脑不能访问镜像仓库，可先在开发电脑通过 `docker save -o ipc-gateway-image.tar ipc-gateway:latest` 导出镜像，传输后通过 `docker load -i ipc-gateway-image.tar` 加载，再使用 `NoBuild` 模式发布。正式使用建议指定固定版本镜像标签，并在导出、加载、发布时保持标签一致。
Docker Desktop 应使用 Linux 容器模式，镜像架构应与目标主机一致；x64 开发电脑生成的默认镜像不应直接视为 ARM64 镜像。
远程访问时，网站地址为 `http://目标机器IP:5184`；Windows/Linux 裸机安装默认绑定 `127.0.0.1`，需要远程访问时显式配置监听地址及对应网络访问规则。

## 验证范围

仓库不再携带测试代码或模拟器。发布前构建前后端，核对发布清单，并按 [发布验收清单](发布验收清单.md) 和 [浏览器验收清单](浏览器验收清单.md) 验收目标环境。
