# 项目配置 Protobuf 存储说明

## 存储范围

项目配置包含通道、设备、连接参数、分组、标签、清洗转换、传统规则和流程规则，统一使用真正的 Protobuf 字段编码，不是在 Protobuf 中包裹 JSON，也不通过 Base64 保存二进制。

| 场景 | 当前格式 |
| --- | --- |
| `ProjectConfigStore` 项目文件 | `.pb` 二进制文件；默认 `Data/gateway-project.pb` |
| 数据库 `gateway_configurations` 中 `config_type = project` 的版本 | `payload_binary` 二进制列；原 `payload` 留空 |
| 安装升级界面的项目备份与恢复 | `.pb` 二进制备份；包含项目、MQTT、OPC UA、历史和存储健康配置 |
| `appsettings.json`、生产启动参数、REST API | 继续使用 JSON |
| 数据库中的其他配置类型、运行快照、审计与历史数据 | 本次不更换格式 |

数据库列按提供程序使用 SQL Server `varbinary(max)`、PostgreSQL `bytea`、MySQL `longblob`、SQLite `blob`。

## 现有项目转换

数据库迁移 `202611100001_project_protobuf` 在首次启动时执行：为配置表添加二进制列，分批读取全部现有项目版本（含历史版本），转换为 Protobuf 后清空对应的旧文本。项目 ID、版本号、活动状态、创建时间及加密后的凭据保持不变。转换失败会抛出包含版本号的异常，不将损坏的项目视为默认项目。

这段 JSON 转换代码仅属于一次性数据库迁移；正常保存、加载和版本回滚只使用 Protobuf，不尝试读取 JSON。已有单独的 JSON 项目文件或 JSON 备份不再接受，请在升级前确认数据已进入配置数据库；升级前导出数据库备份。新格式启用后，回退到仅支持 JSON 的旧程序需要同时恢复旧数据库备份。

MySQL 的新增列语句有隐式提交行为，列存在检查允许转换失败后重试；项目数据的转换另起事务。其他数据库的新增列和转换沿用迁移事务。每批最多取 32 个版本，避免一次把所有项目版本载入内存。

## 开发维护约定

- 编解码入口：`src/IPC.Gateway.Core/Configuration/ProjectProtobufCodec.cs`。
- 固定字段编号：`src/IPC.Gateway.Core/Configuration/ProjectProtobufContracts.cs`。新增字段只能追加新编号，已使用的编号不得重排、复用或随属性顺序重新生成；属性通过 `nameof` 引用。
- 枚举的数值也是持久化协议的一部分，新增枚举项应追加或显式指定新值，不得重排已有值。
- 项目文件和备份分别携带格式标识与版本号，不能互相替代。破坏性修改需要增加格式版本并提供明确迁移。
- 反序列化跳过包含业务默认值的构造函数，确保显式保存的 `false` 和 `0` 不会被默认值覆盖；缺失的字符串和列表恢复为空值。时间保留 `DateTime.Kind`。
- 数据库存储前仍执行原有校验、克隆与凭据保护；备份仍沿用应用服务的凭据脱敏规则。
- 项目文件通过同目录临时文件写入后替换；二进制文件无法手工编辑，现场调整通过界面完成。

## 界面操作

在“安装升级”页面的“项目备份”卡片点击“导出备份”，下载 `.pb` 文件。恢复时选择或拖入该文件，确认后写回项目和相关配置。恢复期间网站显示保存遮罩，完成或失败后解除。
