# 三节点热备与防双主实施方案

**设计稿，2026-11-23。** 两台业务网关 A、B 互为热备，第三台机器 C 只参与仲裁。A 断电、挂起或失去仲裁网络时，只要 B 已准备好、B 和 C 能形成多数派、A 的旧租约已安全到期，B 自动接管。现场无需虚拟化平台、带外管理或 A 的退出回执。SQL Server 等数据库可继续承担业务存储；授主、续约和 PLC 写授权均由独立的三成员仲裁服务决定。

## 1. 业务边界与接管分界线

工程、接口、驱动落点和“系统 → 高可用”页面交互见[三节点热备代码与界面改造设计](三节点热备代码与界面改造设计.md)。

**接管时刻取多数派提交“业务主机由 A 变更为 B”的日志位置。** 同一集群内，每次具体 PLC 写授权和每次切主都进入同一条有序日志。PLC 写授权排在切主之前，属于旧任期已批准的操作；排在切主之后，旧主的申请必须被拒绝。审计和验收按提交顺序判断，两个操作系统的墙上时钟只用于显示。

| 切主时，一笔写处于什么状态 | 处理约定 |
| --- | --- |
| 在 A 的网页上点过写入，或已在设备队列中排队 | 尚未授权。B 接管后，A 必须拒绝这笔写入。 |
| A 已通过用户权限、标签权限或本地任期检查 | 仍须取得这一次具体写入的多数派授权。 |
| 多数派已批准 A 发送这笔确切的命令，A 随后被暂停 | 属于接管前授权。原执行实例恢复后可能完成这一次发送，现场接受这一边界。其他实例、命令、分段或重试不能复用这份授权。 |
| A 已发包，但报文迟到或回包丢失 | 不追溯网络交付时刻。结果无法确认时标为“执行结果未知”，B 不自动重放启动脉冲、复位等命令。 |
| A 已失联，B 和 C 仍互通 | 旧租约安全到期且 B 就绪后自动授予 B 新任期。A 即使仍能访问 PLC，也拿不到新写授权。 |
| 只有一个仲裁成员可用 | 拒绝新的 PLC 写授权和升主。当前主机最多在本地安全期限内维持已有主业务，期限到后降级。 |

**示例。** 提交索引 410 批准 A 向某台西门子 PLC 的 `DB1.DBW0` 写入 1，索引 411 将主身份从 A 交给 B。即使 410 对应的报文稍晚到达，仍属于已批准的那一次写入。A 队列里还有一笔同地址写入 2，尚未获批；它在 411 之后申请时必须被拒绝，即使这笔命令比 410 更早入队。B 用新任期申请写入 3 可以获批。验收据此核对命令身份和授权序号，PLC 单个寄存器的最终数值无法单独证明整个过程。

本方案保证**受控网关入口的写授权唯一且有序**。PLC 的物理执行时刻、外部工具直接访问 PLC、绕过网关接口自行发包的程序超出这一保证。报警、邮件、Webhook、MQTT 等对外投递分别处理幂等与重放。获得主身份也不代表每台 PLC 当时都已恢复采样。

## 2. 部署拓扑与代码拆分

| 节点 | 常驻进程 | 角色 |
| --- | --- | --- |
| A、B 各一台 | 网关业务进程 + 独立的仲裁成员进程 | 两台均可预热，任一时刻仅一台获得有效业务主身份 |
| C | 独立的仲裁成员进程 | 投票并持久化仲裁记录，可当选仲裁领导者，永远不运行 PLC 业务 |

生产将三成员分散到三个独立故障域。一次单机故障后，另外两名成员需要保持互通且可持久写盘。仲裁领导者负责提交决定，业务主机负责采集和发布。仅发生仲裁领导者变更时，现任业务主机应能延续有效授权，避免 PLC 全部重连。

建议新增两个工程，沿用 .NET 10：

- **IPC.Gateway.Arbiter**：独立服务，包含成员间共识、持久化日志和快照、业务授权状态机、节点证书认证、状态查询与审计。启动不依赖项目数据库、PLC、历史索引或 WebHost。采用有持久化实现的 Raft 库，技术验证可先评估 DotNext，须实测目标平台上的落盘、崩溃重启和版本兼容。DotNext 默认共识存储只在内存中，客户端去重也需应用实现。[Raft 库说明](https://dotnet.github.io/dotNext/features/cluster/raft.html)
- **IPC.Gateway.HighAvailability**：由网关使用，负责仲裁客户端、业务实例身份、续约、预热检查、升降主、写授权及运行指标。保留单机部署模式。配置为热备的实例若缺证书或无法形成多数派，应保持待命，禁止自行回退为单机主机。

每个成员配置固定集群 ID、成员 ID、跨主机可达的公告地址、独占持久卷和节点证书。每次业务进程启动产生新的实例 ID。成员和业务客户端使用双向 TLS，证书绑定节点及角色，管理员与机器分权。集群仅首次显式初始化；重装、容器重建、空卷或旧备份恢复均不得静默创建新集群。失去全部可信状态时，按灾难恢复流程停用旧集群身份、核实业务实例并重新登记。

现场先安装三个仲裁成员及 A/B 网关，再从任一网关进入“系统 → 高可用 → 高可用配置”完成一次组网。保存草稿、三端预检与实际启用分别执行。上线后允许调整首选主机和租约策略，集群身份及成员替换由维护流程管理。

## 3. 仲裁状态机与授主流程

持久化状态至少包括集群身份、成员配置、业务主节点及实例、业务任期、租约版本、切换请求、近期命令去重信息和提交索引。**业务任期**在每次重新授予业务身份时递增，独立于 Raft 选举任期。变更经多数派持久提交并应用后才向调用方返回成功。落后成员可以显示带索引的诊断状态，不能依据本地旧状态授主或批准写入。

| 建议的操作 | 条件和结果 |
| --- | --- |
| 报告就绪状态 | 上报项目版本、程序兼容版本、插件签名与版本、证书、脚本模型校验、维护状态和业务线程进度。心跳本身不延长租约。 |
| 申请主身份 / 续约 | 校验集群、候选资格及实例。续约只接受当前持有者和当前业务任期。重启前发出的迟到请求不能使旧实例复活。 |
| 交接 / 授予新任期 | 计划交接时由 A 停收新写、清理旧任务并提交退出确认，可提前切换。故障时由多数派等待旧租约安全到期后提交接管。切换一旦提交，A 的后续写授权立即失效。 |
| 批准单次 PLC 写尝试 | 校验主实例、业务任期、有效租约、命令身份及内容摘要。在与授主相同的状态机内决定是否批准。禁止将授权预分配到未来的队列。 |
| 查询状态与结果 | 返回当前任期、主机、提交索引、备机是否就绪、原因及某一命令的处理状态。查询旧命令的结果不会再次触发发送。 |

**时间设计。** 首轮联调从每 1 秒续约、5 秒租约开始，这两个数是压测起点。业务客户端从发出续约请求起使用单调时钟计算提前停用期限，预留网络往返、调度延迟和时钟漂移余量。迟到回应不能恢复已过期的本地授权。仲裁领导者变更或集群重启后，先恢复已提交状态；若无法证明上一次租约已安全到期，须从重新建立多数且确认旧记录后保守等待完整安全窗口，或接受旧主已提交的主动退出。进程暂停、系统休眠恢复、时钟跳变列入测试。租约失效一旦提交，和续约按同一顺序处理。状态机应用结果应可重放，禁止各副本在应用同一命令时读取自己的当前时间来决定授主。

**挂起检测。** 仲裁进程与业务进程分别存活。只有业务进程能以自身实例身份、携带近期的调度进度证明请求续约。进度应来自受监督的业务循环，空项目或全部 PLC 离线时也应能产生进度。某一个 PLC 连不上或某个点读取慢，按既有坏点和设备重连策略处理。

## 4. PLC 写入如何落到驱动

1. API、网页、OPC UA、普通 MQTT、Sparkplug 和脚本沿用原有权限及类型检查。设备写队列保留顺序，入队时生成逻辑命令 ID、绑定来源实例和目标配置版本。备机应尽早拒绝本机写入并给出稳定业务入口，禁止客户端自动重发有副作用的写请求。
2. 到队首、目标解析和连接准备完成后，确定具体发送尝试。授权绑定集群、主节点、实例、业务任期、逻辑命令 ID、尝试 ID、设备及连接目标、地址、类型、偏移、数量、写值摘要和配置版本。诊断临时设备也要绑定协议和实际连接目标。授权等待使用异步超时，不占用全局采集锁。
3. 仲裁集群提交批准后，只有原实例中对应的这一次执行可以发送。重复 RPC 要识别同一尝试；相同 ID 携带不同内容须拒绝。并发请求不能重复消费授权。应持久标记已进入发送阶段，避免同一命令在崩溃恢复时再次发包；授权回应丢失、进程重启或发送结果不明时，不以旧授权在其他实例上补发。规定命令去重期限，并拒绝超龄重放。
4. 应用层重试、重新连接后重发、拆包写数组等后续 PLC 写尝试分别取得授权。先读取再写入的驱动在实际写操作前检查。协议传输层自行重传同一已提交报文属于已接受的传输边界。插件若隐藏多次业务写入，应接入统一发送接口；尚未验证的驱动在热备模式下只开放已验证能力。
5. 审计分别记下“拒绝、已授权、已下发、设备确认、结果未知”，关联任期、提交索引、逻辑命令和尝试。PLC 与仲裁之间没有原子事务，成功取得授权不等于设备执行成功。切主不会清除尚待核实的写结果。

普通采集批读继续使用本机有效角色与租约。只有 PLC 写尝试需要多数派确认，因此其延迟会增加一次多数派提交的成本。需测量高频写入与批读竞争设备连接时的影响。若以后采用日志批量提交，可将多笔已经确定且各有独立身份的写授权一起落盘，仍需保留每笔与切主的先后关系。

驱动验收示例：现有 [Modbus TCP 写入适配器](../src/IPC.Gateway.Core/ModbusTcp/NModbusMasterAdapter.cs) 会拆分数组写入。第一片获批后发生切主，后续片必须重新申请。结果应能表达“部分写入”，保留最后已确认的片段；回读或人工核实后再决定如何处理。自定义驱动的签名用于验证来源，热备写入能力要另行验证。

## 6. 配置、报警和北向服务的接续

- **配置与凭据。** A、B 共用权威项目版本。配置写入按业务任期及期望配置版本原子校验，数据库迁移串行执行。业务密钥通过显式配置提供；节点各有自己的机器证书。项目版本、加密凭据、插件、脚本、模型或必要证书未就绪时，显示阻塞原因。仲裁可用与业务数据库可用分别检查。
- **实时值与规则。** 接管后按设备并发限流重连，点位从“等待首次采集”开始，首个有效样本到达后更新。采样空白不计入已观测的连续无变化时长。窗口、节拍与清洗状态第一版按规则语义重新建立；需要跨机连续计算的节点后续增加带版本检查点。
- **报警与关键投递。** 报警历史、未闭环记录、人工处理状态和关键待发消息应有 A、B 都可接管的事务存储。现有 [报警日志](../src/IPC.Gateway.Core/EdgeGateway/GatewayAlarmJournal.cs) 与 [普通 MQTT 文件队列](../src/IPC.Gateway.Core/EdgeGateway/MqttOutboxStore.cs) 均需制定迁移或同步策略。首版建议复用共享业务库承载报警和关键投递，按记录 ID 与认领状态接续；普通遥测按现有消息策略决定保留或合并。MQTT、Webhook、邮件等已发送但未保存确认时可能重复，使用稳定事件 ID，接收方具备能力时去重。
- **点位历史。** 保留主机本地分卷写入，封卷校验复制，活动卷按已确认偏移增量复制，备机按复制进度恢复索引。历史缺口、最后同步位置及可接受的数据丢失窗口单独验收。仲裁日志只保留控制信息和授权元数据。
- **北向身份。** MQTT 使用同一个逻辑网关身份，由当前主机连接，处理旧遗嘱和新主状态的先后。OPC UA 使用稳定端点和点位 NodeId，预先配好客户端可验证的身份与证书，切机后由客户端重新连接和订阅。Web 登录凭据、权限和业务入口应在两台机器一致。串口、USB、仅允许单一源 IP 或配置为本机回环地址的设备，要先验证 B 确实可达。

## 7. 发布、升级与运维

| 环境 | 安装与升级方式 |
| --- | --- |
| Windows 服务 | 分别发布网关和仲裁服务。A、B 安装两个服务，C 只安装仲裁。服务各有身份、状态目录和证书访问权限。扩展现有中文安装、卸载和打包脚本。 |
| Linux systemd | 提供独立网关与仲裁 unit、环境文件和可写目录，仲裁的绑定地址和公告地址支持跨机。继续采用发布包加宿主机脚本更新。 |
| Docker | 分别构建版本化网关和仲裁镜像。每个宿主机固定成员身份、地址及独占持久卷。容器重建恢复原成员，替换损坏成员需显式登记。使用镜像滚动更新。 |

热备部署覆盖上述三种方式及其混合组合。IIS 进程内托管不纳入热备验收，应用池回收、空闲停止和回收期间进程重叠会让网站、采集、仲裁共享生命周期。现场如需 IIS，可仅用它反向代理独立服务。

每次只维护一个投票成员，开始前确认另两票健康，完成后等待追平；维护业务主机前先计划交接。升级包声明程序、协议和持久化格式兼容范围。程序回滚不得回滚仲裁卷或复用旧任期。界面建议增加“高可用”页，展示三成员、业务主备、任期、多数可用性、同步差距、不可接管原因、切换记录和结果未知的写操作；管理操作做权限与审计，支持中英文。

## 8. 实施顺序与验收

1. **仲裁原型。** 三平台验证所选库的多数派提交、持久化、快照、重选、成员替换和请求去重。交付独立仲裁服务与安装产物。
2. **业务角色改造。** 拆分预热与激活，接入租约、配置重载和看门狗。先打通计划交接，并验证现有单机模式。
3. **写授权与自动接管。** 收口所有已支持协议的写入口、分段和重试。接入租约到期自动授主，完成断电、挂起和单向断网测试后，再开放自动接管配置。
4. **业务连续性与投产。** 接续报警和关键队列、处理历史同步、接入统一业务入口，执行滚动升级与混合平台压测。按认证过的平台、驱动和能力列出支持范围。

| 验收场景 | 合格判据 |
| --- | --- |
| A、B 同时启动；C 当选或更换仲裁领导者 | 最多一个已授权业务主机；只换仲裁领导者不强制重启健康的 PLC 会话。 |
| A 整机断电；另一组测试仅暂停 A 的业务进程而保留其仲裁进程 | 两组均须在旧租约安全到期、B 与 C 达到多数且 B 就绪后自动接管；不等待旧主。仅单个设备离线不触发切主。 |
