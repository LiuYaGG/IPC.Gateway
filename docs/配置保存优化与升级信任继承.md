# 配置保存优化与升级信任继承

## 配置保存

- 数据库仍按JSON保存完整配置和版本历史。改为紧凑JSON，不删除字段，不改变现有读取和回滚格式。
- 保存新版本或回滚激活旧版本时，只停用当前 `active=true` 的记录，不再更新全部历史记录。
- 已核对数据库迁移：配置类型与版本号、配置类型与激活状态的索引原本已经存在，本次不重复创建索引。
- 设备、通道、分组、标签和规则的常规新增、编辑、删除API统一经过网关配置互斥门。获得互斥门后才读取最新项目，并完成修改、持久化和运行时应用，避免不同标签的并发修改相互覆盖。
- 相同项目配置跳过配置版本写入和运行时重载；审计日志仍按原策略记录。编辑同一个标签的完整表单仍采用后保存内容，不属于字段级协作编辑。
- 保存标签时保留原编辑窗口，只在保存按钮显示加载状态，不再额外弹出“正在保存配置”窗口；保存期间标签表单、取消、关闭和菜单切换仍受保护，防止重复提交和修改待保存内容。其他配置写请求仍显示保存遮罩。浏览器刷新或关闭页面会弹出离开提醒。采集和推送继续运行。网络中断时后端仍可能完成保存，不能将网络报错理解为数据库回滚。

## 运行服务更新

- 设备配置修改时，OPC UA 使用增量地址空间同步，不再每次停止并重新启动整个Server。现有变量尽量复用；新增节点注册、删除节点移除，更名或数据类型变化时删除旧节点并创建新节点。
- 删除节点时先更新状态、移除浏览引用和预定义节点，再删除运行时映射；旧节点写入回调还会检查节点是否仍存在。
- 未改变NodeId和数据类型的节点可保留其对象和订阅。名称路径改变的节点需客户端订阅新NodeId；客户端自己的浏览缓存可能需要刷新。
- 仅修改标签说明时，不重建规则引擎；其他影响编译依赖的配置变化仍保守地重建规则引擎。
- 完整项目重载、配置回滚、Server安全策略等操作仍可按原逻辑重启服务，不能等同于普通标签增量修改。

## 分段日志

应用日志目录为宿主目录下的 `Data/Logs`，新增记录：

- `ConfigurationMutationGate`：等候配置互斥门的时间。
- `ConfigurationSaveTiming type=project.prepare`：规范化和校验、克隆和敏感字段保护、序列化的时间，以及实际JSON字节数；其总耗时还包含后续保存。
- `ConfigurationSaveTiming type=project`：创建数据库客户端、打开连接、开始事务、查询版本、停用当前版本、插入新版本、提交事务的时间。
- 原有 `GatewayReloadTiming` 中，普通设备配置应用的 OPC UA 阶段改为 `SyncOpcUa`。

## 驱动升级后无需再次签名

旧DLL的RSA签名不能验证新DLL。本次新增的是本机受控升级的信任继承，不是假装旧签名仍然有效。

1. 在准备和执行升级时，系统校验原ZIP及文件摘要，并重新提取有效载荷。
2. 仅对升级前已经通过可信公钥验证（或已完成合法继承）的驱动，检查新旧驱动包标识是否一致。
3. 将新DLL摘要、驱动清单元数据、公钥指纹、升级包ID及升级包摘要绑定，保存在可信公钥旁的 `.upgrades.json` 文件中。
4. 升级后的驱动必须匹配该记录，才能在强制验签开启时加载。界面显示“升级可信”，操作列显示“-”，无需再次导入原私钥。
5. 直接替换或篡改DLL、改变清单的受绑定信息、更换可信公钥，均不会自动获得原记录的信任。

可信公钥及升级继承记录所在目录属于安全配置目录，应与公钥本身使用相同的文件权限保护，备份时一并保留。不保存原驱动私钥，也不修改升级包中已校验的清单文件。

首次从旧版本升级时，旧宿主可能还没有生成继承记录。新宿主会根据待执行升级记录、仍保留的原ZIP和回滚副本中的旧驱动签名恢复信任，并在需要时重新加载驱动。缺少原包、回滚副本或有效旧签名时不能补造信任，需要正常重新签名。

该机制适用于系统内“准备升级/重启升级”及其生成的离线动作。手动解压覆盖程序目录、全新安装、升级包缺少有效文件摘要、驱动包标识变化，不承诺自动继承信任。关闭或删除可信公钥后，继承记录也不再授予信任。

## 验证状态

按本次要求，仅完成前后端编译和静态检查，未运行功能、数据库、并发、压力或升级实测，未修改当前数据库，未发布服务。实际性能改善幅度需部署后依据分段日志确认，不将历史24秒保存耗时作为当前已消除的实测结果。
