# 心跳与连续无变化超时规则

## 配置方法

在规则引擎新增或编辑流程，连接：

**标签输入 → 连续无变化超时 → MQTT 发布／邮件通知／Webhook**

在标签输入中选择 PLC 心跳位或心跳计数器，在“连续无变化超时”节点配置：

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| 无变化超时（秒） | 30 | 从首次正常样本或最后一次有效值变化开始，完整经过该时间后触发 |
| 变化死区 | 0 | 数值变化超过此值才重新计时；0 表示检测任意数值变化 |
| 数据最大间隔（秒） | 10 | 正常采集的样本时间间隔允许上限，超过后暂停卡死判断 |

例：心跳每秒变化一次、网关每 500 毫秒采集，设置无变化超时 10 秒、死区 0、数据最大间隔 3 秒。心跳计数持续增加时不报警；采集正常但心跳连续 10 秒不变时报警；心跳再次变化时发送恢复事件（动作启用恢复通知时）。

数据最大间隔应大于实际采集周期及正常抖动，并小于无变化超时，使采集停更优先被识别。通信/读取失败可另配“标签输入 → 质量门控 → 持续确认 → 通知”规则。质量门控是点位质量判断，并不直接代表设备整体 Online/Offline；地址错误也可能使点位质量异常。

## 判断语义

- 首次收到正常且未过期的样本才开始计时，不从旧缓存时间补计，不在启动时直接报警。
- 每次有效值变化立即重新计时；`10 → 20 → 10` 算两次变化，不会因为首尾相同误判。
- 支持 Bool、数值、字符串和常见数组；字符串及 Bool 使用精确比较，数值按死区比较。数组按元素比较，并保存独立基线副本。
- 死区相对上次有效变化的基线计算，避免每次小幅漂移导致永远检测不到累计变化。64 位整数心跳不会先转为 Double 而丢失相邻整数精度。
- 上游配置了数值处理时按处理后的数值判断；未配置处理时直接比较点位的处理值，不把大整数强制转浮点。
- 周期检查直接读取运行时最新采集快照。即使值不变、不产生变化事件，也能持续确认采集是否正常；定时器不会把旧快照的时间改成当前时间伪造新数据。
- 质量异常、数据停更、标签移除或无效数值时，取消待触发/待恢复的确认计时。采集恢复后重新计算完整无变化时长。
- 已有的卡死报警在通信异常时保持，不发送虚假的心跳恢复；恢复采集后，只有观察到有效变化才清除此报警。
- 沿用持续确认、恢复确认、告警生命周期和动作策略。另接“持续确认”会在无变化超时之外增加确认等待时间。
- 相同规则配置在进程内重建服务时保留计时状态；进程重新启动后重新观察完整时长。暂停期间的采集大间隔不计为有效连续观察。

检测基于网关实际采集到的样本。心跳变化应比采集周期慢，避免翻转多次后采到相同值；计数器通常比快速翻转位更便于检查。定时检查周期约 250 毫秒，实际触发还受系统调度和配置的确认时间影响。

当前组合/顺序节点仍只接受基础条件，这个高级时间节点可连接输入、数据处理、质量门控及下游确认/通知节点，不扩展为任意高级节点的 AND/OR 组合。

## 实现与存储

新节点类型和条件类型为 `NoChangeTimeout`。项目的普通规则与流程节点均追加三个 Protobuf 字段编号，不修改已使用编号。相关配置经 API、手工克隆、两套规则编译路径、项目文件、数据库和备份沿用同一套字段映射。

测试使用内存采集服务及模拟时间验证，不连接业务 PLC，不修改数据库。后端验证首次计时、精确超时边界、变化恢复、翻转回原值、采集间断、质量异常、数组、64 位计数、运行时重建、两套编译器及 API/Protobuf 往返。

## 质量门控通知修复

独立的“标签输入 → 质量门控 → MQTT 发布”流程会在启用时评估已有快照，包括已经断线的点位。已修复通知队列对 `Quality:Bad` 等带冒号状态的误判：原逻辑去掉了冒号前的状态名，导致实际已触发的质量事件被当成过期动作而丢弃。现在先匹配完整状态，只对引擎生成的 `Escalated:` 和 `Retriggered:` 生命周期前缀做特殊处理，真实过期动作仍会被拒绝。

质量门控选择“包含所有状态”时，Good 也匹配，因此不会因为恢复正常而解除报警。用于异常检测时可包含 `NotConnected,Bad,ReadError`，也可结合实际点位状态进一步收窄；这些状态包含点位读取错误，不等同于精确的设备 Online/Offline 事件。
