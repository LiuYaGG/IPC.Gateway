# OPC UA 统一入口与主备切换

网站与 WebAPI 继续使用 C 的 HTTP/HTTPS 入口。OPC UA 独立使用 TCP 入口：

`客户端 → opc.tcp://192.168.164.128:4840/IPC.Gateway → 当前业务主机 A 或 B 的 4840`

## 网关网页配置

更新 A、B 后，在“通信 → OPC UA Server → 连接”配置：

| 字段 | A、B 推荐值 |
| --- | --- |
| 监听主机 | `0.0.0.0`，或该网关自己的本机 IP |
| 监听端口 | `4840` |
| 端点路径 | `IPC.Gateway` |
| 对外公布端点 | `opc.tcp://192.168.164.128:4840/IPC.Gateway` |

本地监听地址与对外公布地址分别展示。不能把 A、B 的监听主机填成 C 的 IP，C 的 IP 不属于 A、B。对外公布端点可使用稳定 DNS 名称；代理端口可以与本地端口不同，但路径必须相同。留空公布端点可用于无代理的单机部署。

这些选项通过共享业务库保存，因此 A、B 通常共用配置。监听 `0.0.0.0` 可避免共享配置绑定另一台主机的 IP。对外公布地址变更使用正常配置保存流程；备机在预热或启动业务时加载并校验证书。

在“证书”页，可按行填写“证书附加 IP / DNS”。公布端点中的主机名/IP 自动加入 SAN，不必重复填写。修改地址或附加名称后，如果本机证书缺少这些名称，网关将归档本机原应用证书及私钥并生成新证书。其他客户端信任证书不会被清空。A、B 分别保留自己的私钥，不复制彼此的私钥目录。

修改证书后，客户端需要重新信任 A、B 的新服务端证书，并检查证书中的统一入口名称。A、B 保持相同逻辑 Application URI、标签命名空间、端点路径和安全模式/策略。这里不改变现有匿名访问、客户端自动信任或安全策略的选择。

## C 的 HAProxy 配置

将[OPC UA 参考配置](参考配置/haproxy-opcua.cfg.example)追加到现有 HTTP 配置末尾，保留原网站与 WebAPI 代理段。参考地址为 A `192.168.110.154`、B `192.168.164.131`、C `192.168.164.128`；现场地址或端口变化时相应调整。

`/health/opcua-active` 同时检查“本机具备业务主身份、业务启动就绪、OPC UA 已启用且正常运行”。探针通过管理端口 `5184` 发 HTTP 请求，业务字节通过 `4840` 转发。只有一台探针健康时才接入，不对 A/B 轮询，也不把单纯端口开放视为可以发布。

如果原健康检查要求 API Token，沿用同一认证方式；若要求 HTTPS，使用实际 HTTPS 端口与可信证书配置。不要为了探针关闭已有认证或证书检查。保留各自的 OPC UA Sign/SignAndEncrypt 端到端安全，TCP 代理不加 HTTPS `ssl` 终止，也不添加 `send-proxy`。

在 C 原生系统修改配置后，先校验配置，再重载当前 `ipc-gateway-proxy.service`。如果改变 TCP 端口，同时调整防火墙及 Docker 端口映射。监听地址和证书公布地址的设置不会代替操作系统网络配置。

## 验收

1. A、B 的 `/health/opcua-active` 应分别返回一台 `200 {"active":true}`、一台 `503 {"active":false}`；关闭 OPC UA 后，网站仍可访问，但 UA 探针应返回 503。
2. 客户端连接统一端点，GetEndpoints/FindServers/CreateSession 返回的地址应仍是统一入口，不应跳回 localhost、通配地址或某台后台机器。
3. 分别信任 A、B 的证书，验证加密连接、浏览、读取和授权写入。
4. 计划切换，观察旧连接断开后客户端重新发现、建立新会话、重建订阅，标签完整路径保持一致。

当前实现不复制 UA SecureChannel、Session 或订阅到另一台机器。TCP 代理不能把既有会话迁移到新主机，客户端必须具备新会话与订阅恢复能力；不保证切换期间每一个中间通知都能补回。写入过程中连接断开时结果可能未知，应先核对设备结果，不盲目重复有副作用的写操作。

C 同时承载 HAProxy 时，C 下线也会使统一入口下线。人工灾难接管后可直连存活网关；入口本身的双代理/VIP 冗余需要另行部署。
